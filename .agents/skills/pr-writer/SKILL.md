# PR Writer

완료된 브랜치의 변경을 `.github/PULL_REQUEST_TEMPLATE.md`에 맞춰 정리한다. Git과 이슈에서
확인한 사실만 사용하고 완료 여부를 과장하지 않는다.

```text
브랜치·커밋·diff·이슈 수집
  → 제목·본문 초안 작성
  → [GATE] 사용자 검토 및 승인
  → gh로 PR 등록 또는 로컬 저장
```

초안 작성 단계에서는 코드, 커밋, staging, 원격 상태를 변경하지 않는다. 저장, push, PR 생성은
각각 사용자의 명시적 승인을 받은 범위에서만 수행한다.

## 1. 근거 수집

### 브랜치와 이슈 번호

`git branch --show-current`로 현재 브랜치를 확인한다.

- `type/#N/설명` 또는 `type/N/설명`에서 `type/` 뒤 첫 숫자를 이슈 번호로 사용한다.
- 번호가 없으면 임의로 만들지 말고 사용자에게 묻는다.
- `main`이나 `develop`이면 대상 작업 브랜치를 먼저 확인한다.
- Git이 dubious ownership으로 실패하면 현재 저장소의 절대 경로만
  `git -c safe.directory=<현재 저장소> ...`에 지정한다. 전역 Git 설정은 바꾸지 않는다.

### 베이스와 변경 범위

기본 베이스는 `develop`이다. 로컬 `develop`이 없으면 `origin/develop`, 그마저 없으면 `main`을
사용하고 폴백 사실을 알린다.

다음을 읽기 전용으로 확인한다.

```text
git log --oneline <base>..HEAD
git diff --stat <base>...HEAD
git diff <base>...HEAD
git status --short
```

- Conventional Commit 제목과 실제 diff를 함께 확인한다.
- 미커밋 변경은 PR 범위와 명확히 구분한다.
- 여러 목적이 섞였으면 기능, 테스트, 문서, 리팩토링으로 나눠 설명한다.
- 현재 이슈의 완료 조건을 막지 않는 아이디어는 `기타 · 후속`으로 분리한다.

### 이슈와 프로젝트 문서

- 가능하면 `gh issue view <번호>`로 이슈 본문, AC, 의존성을 확인한다.
- 네트워크 또는 인증이 필요하면 현재 Codex 환경의 승인 절차를 따른다.
- 관련 `docs/features/**/issue-<번호>.md`와 기획 문서를 확인한다.
- 문서와 코드가 다르면 실제 커밋과 diff를 우선한다.
- 구현되지 않은 요구사항은 완료로 쓰지 않고 후속으로 표시한다.

## 2. 초안 작성

`.github/PULL_REQUEST_TEMPLATE.md`를 처음부터 끝까지 읽고 이를 단일 구조 기준으로 삼는다.

- 헤딩과 표의 의미를 유지한다.
- 작성 안내용 HTML 주석과 빈 예시는 최종 본문에서 제거한다.
- 해당 없는 선택 섹션은 템플릿 안내에 따라 삭제하거나 `없음`으로 표시한다.
- 템플릿에 없는 고정 섹션을 임의로 추가하지 않는다.

### 작성 규칙

- 제목은 `[type] 한 줄 요약` 형식으로 제안한다.
- 본문은 격식체로 쓰고 변경 이유, 주요 흐름, 리뷰 지점을 구체적으로 설명한다.
- 변경 유형은 실제 커밋과 diff에 해당하는 항목만 선택한다.
- 현재 PR에서 달성한 AC만 `[x]`로 표시한다.
- 직접 성공을 확인한 검증만 `[x]`로 표시하고, 미실행·실패 항목은 `[ ]`로 둔다.
- PR 머지와 후속 구현처럼 아직 일어나지 않은 작업은 `[ ]`로 둔다.
- 테스트 실패, 미커밋 변경, 알려진 제약을 숨기지 않는다.
- 의존성을 확인할 수 없으면 추측하지 말고 `확인 필요`로 표시한다.

검증 명령은 저장소에 실제 존재하고 변경 범위에 맞는 것만 기록한다. 명령을 실행하지 않았다면
실행한 것처럼 쓰지 않는다.

## 3. [GATE] 사용자 검토

제안 제목과 완성된 본문 전체를 사용자에게 보여준다. 사용자가 승인하거나 수정 요청이 모두
반영되기 전에는 파일 저장, push, `gh pr create`를 실행하지 않는다.

수정 요청이 있으면 초안을 고쳐 다시 검토받는다.

## 4. 승인 후 처리

승인 후 다음 중 원하는 방식을 확인한다.

1. `gh`로 PR 등록
2. `.local-docs/pr/pr-#<이슈번호>.md`에 로컬 초안 저장

### gh로 등록

1. `gh auth status`로 설치와 인증을 확인한다.
2. 원격 브랜치가 없으면 별도 동의를 받은 뒤 현재 작업 브랜치만 push한다.
3. 승인된 본문을 임시 파일에 저장하고 `gh pr create --base develop --head <브랜치>
--title <제목> --body-file <파일>`로 등록한다.
4. 생성된 PR URL을 전달하고 임시 파일만 정리한다.

`main` 또는 `develop`에 직접 push하지 않는다. 인증이나 등록에 실패하면 원인을 알리고 로컬 저장
방식을 제안한다.

### 로컬 저장

- `.local-docs/pr/`가 없으면 만든다.
- 같은 파일이 있으면 덮어쓰기 전에 사용자에게 확인한다.
- 저장 경로와 이후 등록 방법을 안내한다.

## 완료 체크리스트

- [ ] 브랜치와 이슈 번호를 확인했다.
- [ ] 베이스 브랜치와 비교 범위를 확인했다.
- [ ] 커밋, 전체 diff, 미커밋 변경을 구분했다.
- [ ] 관련 이슈와 문서를 확인했다.
- [ ] PR 템플릿을 기준으로 작성했다.
- [ ] 검증된 항목만 `[x]`로 표시했다.
- [ ] 제목과 본문 전체를 보여주고 승인받았다.
- [ ] 승인 후 선택한 방식으로만 처리했다.
- [ ] 승인 없이 코드, 커밋, staging, 원격 상태를 변경하지 않았다.
