# TDD Red

명세를 실행 가능한 실패 테스트로 바꾼다. 테스트가 수집되고 올바른 이유로 실패하는 상태까지만 만든다.

## 필수 원칙

- `docs/features/**/issue-{N}.md`의 확정 시그니처·시나리오·AC를 정본으로 삼는다.
- 테스트는 한 번에 하나만 작성하거나 수정하고 `-t`로 해당 시나리오만 실행한다.
- 테스트가 요구하는 provider, mock, jsdom 설정 같은 하네스 누락은 이 단계에서 수정한다.
- 실제 동작은 구현하지 않는다. 수집에 필요한 export와 확정 시그니처의 stub만 허용한다.
- stub 본문은 `throw new Error('not implemented')`만 둔다.
- 기존 구현을 Red로 만들기 위해 훼손하지 않는다. 예상과 달리 통과하면 단언을 점검한다.
- 기존 사용자 변경과 부분 staging을 보존한다.
- 저장소 `AGENTS.md`와 사용자 지침이 이 스킬보다 우선한다.

## 워크플로

### 1. 범위 확정

1. 브랜치와 변경 상태를 확인한다.
2. 사용자 지정 이슈 번호 또는 `feat/#N/...` 브랜치와 단일 `issue-N.md`로 이슈를 결정한다.
3. issue 문서 전체를 읽고 시나리오 수와 AC 매핑을 센다.
4. UI 테스트면 디자인 시스템 문서를 읽는다.

### 2. 테스트 표면 준비

- 순수 함수는 입력·출력을 직접 단언한다.
- 훅은 `renderHook`, 컴포넌트는 RTL의 role 중심 쿼리를 사용한다.
- TanStack Query 대상은 저장소의 `renderWithQuery` 같은 기존 wrapper를 사용한다.
- 전역 mock 오염을 막고 각 테스트에서 상태를 초기화한다.
- 모듈 수집이 안 될 때만 확정된 public API와 stub을 만든다.

### 3. 시나리오별 Red 확인

각 시나리오마다 테스트 한 개를 작성하거나 기존 테스트의 하네스만 바로잡고 다음처럼 실행한다.

```bash
pnpm --filter @repo/web exec vitest run --project unit <테스트 파일> -t "테스트 이름"
```

테스트가 수집되고 명세 행동 때문에 실패해야 한다. module not found, provider 누락, 잘못된 mock 같은 환경 실패는 먼저 해결한다.

### 4. 완료 검증

- issue 문서 시나리오 수와 수집된 테스트 수를 대조한다.
- AC별 테스트가 최소 하나 존재하는지 확인한다.
- 관련 테스트를 묶어 실행한다.
- Green 단계가 구현할 실패와 이미 충족된 시나리오를 보고한다.

## 금지 사항

- 테스트를 통과시키는 실제 분기·상태·렌더링 구현
- issue 문서와 다른 시그니처 발명
- 여러 시나리오 일괄 작성 후 전체 테스트 한 번만 실행
- Storybook story를 테스트 대신 사용
- 수집 오류를 행동 실패로 간주
