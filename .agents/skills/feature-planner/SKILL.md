# Feature Planner

아이디어를 실행 가능한 이슈로 변환한다.

```text
spec-original.md 또는 사용자 아이디어
  → 요구사항 인터뷰 → spec-fixed.md
  → PRD 및 기술 결정 → prd.md
  → 수직 이슈 분해 → issues.md
```

각 `[GATE]`에서 사용자 확인을 받고 멈춘다. 확인 전에는 다음 단계 문서를 작성하거나 GitHub 이슈를 등록하지 않는다.

## 시작 전 확인

1. 루트 `CLAUDE.md`와 적용되는 `AGENTS.md`를 읽는다.
2. 관련 `docs/features/**`와 실제 구현·설정 파일을 조사한다.
3. 문서와 설정이 다르면 Current Truth 원칙에 따라 설정을 우선한다.
4. 기존 변경을 보존하고 기획 산출물 외 코드는 수정하지 않는다.
5. 산출물을 `docs/features/{name}/`에 둔다.

## 1단계: 요구사항 인터뷰

`spec-original.md` 또는 사용자 아이디어의 모호성, 엣지 케이스와 결정 사항을 찾는다. 이미 명확한 내용은 다시 묻지 않는다. 질문은 한 번에 하나만 하고 추천안과 이유를 함께 제시한다.

필요한 만큼 확인한다.

1. primary user와 해결할 문제
2. 최소 동작 시나리오 세 개
3. 기존 데이터·API와 저장 방식
4. 빈 값, 중복, 최대값, 동시성
5. 로딩·빈 상태·실패 처리
6. 재사용할 기존 UI와 행동 패턴
7. 성능 및 데이터 크기 제약
8. 후속 기능에 미치는 영향

UI 기능이면 FSD 책임(`_pages → widgets → features → entities → shared`), 디자인 근거, 360px WebView와 터치·스크롤 제약, 현재 테스트 설정의 검증 가능성도 확인한다.

핵심 용어를 하나의 의미로 고정해 `spec-fixed.md`의 용어 정의에 기록한다.

### 산출물과 게이트

`docs/features/{name}/spec-fixed.md`

`[GATE]` 사용자가 명시적으로 확정할 때까지 멈춘다.

## 2단계: PRD와 기술 결정

### PRD 뼈대

`prd.md`에 개요, 범위, 사용자 스토리, 기술 결정, Out of Scope, 용어 정의를 작성한다. 대안 선택 전까지 기술 결정은 TODO로 남긴다.

### 대안 비교

실질적으로 구분되는 아키텍처 세 가지를 데이터 구조, API·상태 변경점, 핵심 동작, 컴포넌트 구조, 기존 패턴, 테스트 용이성, FSD 경계, 디자인 토큰 정합성으로 비교한다. 세 안이 성립하지 않으면 억지로 만들지 말고 이유를 설명한다.

추천안과 트레이드오프를 제시한다.

`[GATE]` 사용자가 대안을 선택할 때까지 멈춘다.

### ADR

선택한 결정을 다음 형식으로 PRD에 기록한다.

```markdown
### 결정 제목

**Context** — 문제와 제약
**Decision** — 선택한 방식
**Alternatives** — 거부한 대안과 이유
**Consequences** — 장점과 단점
```

이번에 하지 않을 일을 Out of Scope에 구체적으로 적는다.

`[GATE]` 사용자가 ADR과 Out of Scope를 확정할 때까지 멈춘다.

### 산출물

`docs/features/{name}/prd.md`

## 3단계: 이슈 분해

PRD를 반나절~하루 안에 Red→Green→Refactor를 완료할 수 있는 수직 슬라이스로 나눈다. 각 이슈만 완료해도 사용자가 관찰할 수 있는 동작이 생겨야 한다. API, 상태, UI를 각각 나누는 수평 슬라이싱을 피하고 선행 결과가 다음 이슈의 입력이 되게 정렬한다.

```markdown
## Issue N: [태그] 제목

### 설명

사용자 가치 중심 설명 1~3문장.

### 구현 범위

수정할 책임과 예상 파일 또는 레이어.

### 완료 조건 (Acceptance Criteria)

- [ ] AC-N (단위|통합: 설명)
  - Given 구체적인 조건과 실제 데이터값
  - When 행동 또는 호출
  - Then 기대 값·개수·문구

### 의존성

선행 이슈 또는 없음.
```

AC는 테스트로 1:1 변환 가능해야 한다. 순수 함수·훅의 독립 동작은 단위, 컴포넌트 렌더링·상호작용은 통합으로 분류한다. Storybook을 테스트로 간주하지 않고 저장소에 실제 연결된 테스트 명령만 전제한다.

### 산출물과 게이트

`docs/features/{name}/issues.md`

`[GATE]` 사용자에게 수직 슬라이스, AC 구체성, 의존 순서를 확인받는다.

## GitHub 등록

기본 범위는 로컬 초안까지다. GitHub 등록 요청이 있어도 먼저 초안을 보여주고 명시적 승인을 받은 뒤 `gh issue create`를 실행한다. 프로젝트 보드 변경도 승인 범위 안에서만 수행한다.

## 금지 사항

- 확인받지 않은 가정을 확정 요구사항처럼 기록하지 않는다.
- 게이트를 포괄 승인으로 미리 통과하지 않는다.
- PRD 확정 전에 구현하거나 이슈를 등록하지 않는다.
- 저장소에 없는 API, 명령, 컴포넌트나 레이어를 전제하지 않는다.
- 명시적 승인 없이 외부 상태를 변경하지 않는다.
