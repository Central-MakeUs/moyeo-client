# 상수 추출 규칙

값을 상수로 뽑을지 인라인으로 둘지 판단한다.
AI가 가장 자주 과하게 하는 일이 상수 추출이다 — padding 값까지 뽑아 파일 상단이 의미 없는 상수로 가득 차는 걸 막는다.

---

## 기본 원칙

> **"관리 포인트인가?"** — 나중에 **기획·정책이 바뀌면 이 값을 찾아서 고쳐야 하는가?**

관리 포인트가 아니면 뽑지 않는다.

## 상수로 추출한다 — 아래 중 하나라도 해당하면

1. **요구사항이 명시했다** — `설정값으로 관리`, `관리 포인트`, `상수로 관리/정의`, `설정으로 분리` 같은 표현이
   기획 문서(`docs/features/…`)에 있으면 해석 없이 상수로 뽑는다
2. **비즈니스·도메인 의미가 있다**
   - 제약값: `MAX_DEADLINE_MINUTES`, `MAX_PARTICIPANTS`
   - 기획이 바꿀 문구: 에러 메시지, 빈 상태 문구, 버튼 레이블 중 여러 곳에 쓰이는 것
   - 도메인 식별자·경로: `INVITE_CODE_PARAM`, `HOME_PATH`
3. **두 곳 이상에서 같은 값을 쓴다** — 단 레이아웃 수치는 예외다. `px-5`가 여러 곳에 나와도 맥락이 다르다
4. **여러 사용처가 공유하는 정책값이다** — 환경값(`NEXT_PUBLIC_*`)의 이름과 기본 처리처럼

> 화면 고유의 본문 텍스트(약관 조항, 안내 문단)는 **인라인**이다. i18n과는 무관하다 (`i18n-policy.md`).

## 인라인으로 둔다 — 수치가 명시돼 있어도

1. **레이아웃·스타일 수치** — padding · margin · gap · 아이콘 크기 · radius. `"여백 20px"`은 디자인 스펙이지 관리 포인트가 아니다
2. **한 컴포넌트 안에서만 쓰이는 값**
3. **순수 구현 디테일** — HTML 속성 값, 명세에 없는 내부 애니메이션 duration

## 판단 순서

```
  ├─ 키워드("설정값으로 관리" 등)가 있나?     → 상수 ✅
  ├─ 비즈니스 의미가 있나 (제약·기획 문구)?   → 상수 ✅
  ├─ 두 곳 이상에서 쓰이나?                   → 상수 ✅ (레이아웃 수치는 제외)
  ├─ 여러 사용처가 공유하는 정책값인가?       → 상수 ✅
  ├─ 레이아웃·스타일 수치인가?                → 인라인
  └─ 그 외 한 컴포넌트 내부 값                → 인라인
```

**위에서부터 본다.** 키워드가 있으면 레이아웃 수치여도 상수다.

## 어디에 두는가

| 범위                 | 위치                                 |
| -------------------- | ------------------------------------ |
| 한 컴포넌트 안에서만 | 그 파일 상단 (컴포넌트 바깥)         |
| 한 slice 안에서      | `{layer}/{slice}/model/constants.ts` |
| 도메인 무관 전역     | `shared/config/`                     |

슬라이스를 넘겨 공유하려고 `shared`로 올리기 전에 **정말 도메인 무관인지** 확인한다.
도메인 값이면 `entities/{slice}/model/`에 있어야 한다.

> moyeo에는 아직 `shared/config/`가 없다. 첫 전역 상수·환경값이 생길 때 만든다.
> 지금 여러 파일에 흩어진 `process.env.NEXT_PUBLIC_*` 직접 읽기는 `shared/config/`로 모을 대상이다 (`docs/work/backlog.md`).

## 네이밍

- `SCREAMING_SNAKE_CASE`, 단위를 이름에 (`TIMEOUT_MS`, `MAX_WIDTH_PX`)
- 무엇의 값인지 밝힌다: `LIMIT` ❌ → `MAX_UPLOAD_COUNT` ✅

## 의심스러우면 인라인

**인라인이 기본값이다.** 재사용이 생기거나 관리 포인트로 승격되면 그때 뽑는다.
상수로 먼저 만든 뒤 되돌리는 쪽이 더 비싸다.
