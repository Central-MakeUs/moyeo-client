# ai-plan

기능이 아닌 무거운 작업을 **실측 → 계획 → 승인** 순서로 시작한다. 기록 규칙은 `.claude/rules/work-record.md`.

## 0. 이 스킬이 맞는지

| 작업                                      | 스킬                                          |
| ----------------------------------------- | --------------------------------------------- |
| 새 화면 · 사용자 기능                     | `feature-planner` (→ test-scenarios → tdd-\*) |
| 하네스·빌드·CI·의존성/SDK 업그레이드      | **ai-plan** (`INFRA`)                         |
| 동작 불변 구조 변경                       | **ai-plan** (`REF`)                           |
| apps/native (브릿지·status bar·제스처 등) | **ai-plan** (`NAT`)                           |
| 여러 화면에 걸친 버그 · 시안 불일치       | **ai-plan** (`FIX`)                           |
| 파일 몇 개짜리 작은 수정                  | 스킬 없이 바로                                |

> 동작 변경과 구조 변경이 **한 작업에 섞이면 쪼갠다.** 검증에서 무엇 때문에 깨졌는지 구분이 안 된다.

## 1. 컨텍스트 수집

1. ID를 정한다 — `{TYPE}-{이슈번호}-{설명}`. 이슈 번호는 사용자에게 묻는다. 없으면 `{TYPE}-{YYMMDD}`
2. `docs/work/`에 같은 작업 폴더가 이미 있으면 그 `plan.md`를 이어서 쓴다
3. 범위 판단은 **`origin/develop` 기준**이다. 로컬 미커밋 상태를 기준으로 잡지 않는다
4. 관련 `.claude/rules/*.md`와 `CLAUDE.md`를 읽는다. 업그레이드면 공식 마이그레이션 가이드도 확인한다
   (Expo는 `expo:expo-upgrade` 스킬, Next는 공식 upgrade 문서)

## 2. 착수 판단

아래에 **근거와 함께** 답한다. 답을 못 적으면 아직 모르는 것이다 — 조사부터 하거나 사용자에게 묻는다.

| 질문                               | 확인할 것                                          |
| ---------------------------------- | -------------------------------------------------- |
| 목표와 비목표가 한 문장씩 나오는가 | 무엇을 바꾸고 무엇을 보존하는가                    |
| 동작을 무엇으로 고정하는가 (`REF`) | 기존 테스트? 없으면 무엇으로 전후를 비교하는가     |
| 되돌릴 수 있는가                   | 브랜치·백업·단계별 커밋 단위                       |
| 다른 작업과 겹치는가               | 진행 중인 브랜치·스택 PR이 같은 파일을 건드리는가  |
| 웹과 네이티브 양쪽에 걸치는가      | 브릿지 계약처럼 한쪽만 배포되면 깨지는 것이 있는가 |

**업그레이드는 feature 브랜치에 얹지 않는다.** `develop`에서 전용 브랜치(필요하면 워크트리)를 따는 것을 계획에 넣는다.

## 4. 순서 체크리스트

웹 코드는 `shared → entities → features → widgets → _pages → _app → app(라우트)` 순서로 계획한다.
아래를 먼저 만들어야 위가 참조할 수 있다. 각 항목은 **그 단계만으로 검증 가능한** 크기로 자른다.

```markdown
- [ ] `[shared]` …
- [ ] `[native]` …
- [ ] `[검증]` pnpm typecheck · pnpm lint · (사용자) pnpm test
```

웹↔네이티브 계약을 바꾸면 **하위 호환 순서**를 명시한다 (예: 네이티브가 새·옛 메시지를 둘 다 받게 → 웹 전환 → 옛 메시지 제거).

## 5. 리스크와 검증

| 리스크 | 영향 | 대응 |
| ------ | ---- | ---- |

**검증 방법을 구체적으로 적는다.** "수동 확인"만 적으면 아무도 안 한다.

| 방법        | 예                                                                   |
| ----------- | -------------------------------------------------------------------- |
| 자동        | `pnpm typecheck` · `pnpm lint` · `pnpm build` · (사용자) `pnpm test` |
| 라우트 진입 | `/home` 진입 → 모임 카드 렌더                                        |
| 실기기      | iOS/Android dev build에서 로그인 → 새로고침 → 세션 유지              |
| 명시적 대조 | 업그레이드 전후 `pnpm build` 경고 목록 비교                          |

## 6. ⏸ 게이트 — 저장하고, 승인받는다

1. `docs/work/{ID}/plan.md`로 **저장한다.** 첫 줄은 `상태: 계획`
2. 사용자에게 **요약 3~5줄 + 파일 경로**로 제시한다. 전문을 대화에 붙이지 않는다
3. 승인되면 첫 줄을 `상태: 진행`으로 바꾸고 체크리스트 순서대로 진행한다
4. 끝나면 `상태: 완료 (YYYY-MM-DD)`, 확정 사항을 기준 문서로 올린다 (`work-record.md` §4)

**승인 전에 코드를 건드리지 않는다.**

## 하지 않는 것

- ❌ 승인 전 구현 시작
- ❌ 착수 판단을 형식적으로 채우기
- ❌ 계획을 대화에만 두기
- ❌ 실측 없이 "영향이 클 것 같다"고 추정하기
- ❌ 진행 중 발견한 범위 밖 문제를 끼워 고치기 → `docs/work/backlog.md`
- ❌ 커밋·push — 스테이징까지만 하고 사용자에게 넘긴다
