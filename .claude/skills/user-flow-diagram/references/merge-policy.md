# merge-policy — 병합 규칙

> `figma.yaml` + `planning.yaml` + `mapping.yaml`([`source-schema.md`](./source-schema.md)) →
> **최종 유저플로우 문서**를 만드는 규칙. 최종 문서는 세 스냅샷의 **파생물**이며 직접 편집하지 않는다.

## 1. 정본 경계

- **Figma 스냅샷** = 화면·흐름(전환)의 정본.
- **Planning 스냅샷** = 식별자·기능 설명·`구분`의 정본.
- **Mapping** = 확인된 연결 관계의 정본.
- 최종 Markdown = 위 셋의 파생 문서.
- **추측 금지 원칙**(한 출처의 정보로 다른 출처의 빈칸을 채우지 않음)의 정본은
  [`source-schema.md`](./source-schema.md) §0이다. 확신 없는 대응의 최종 반영 여부는 아래 §4 게이트가 정한다.
- **충돌하면 자동 선택하지 않고 `unresolved`로 남긴다.**
- 기존 정보는 **해당 출처가 갱신될 때만** 바뀐다(반대편 갱신이 이쪽을 덮지 않는다).

## 2. 병합 순서

1. `figma*.yaml`과 `planning*.yaml`의 출처·동기화 날짜를 확인한다.
2. 변경된 출처의 snapshot만 갱신하고 반대편 snapshot은 보존한다.
3. `mapping*.yaml`의 모든 대응을 재검증한다.
4. 아래 status 게이트를 적용해 최종 문서를 재생성한다.
5. 출처별 신선도 헤더와 미해결 항목을 확인한다.

## 3. 1:N 매핑 (화면번호는 굵은 단위)

- 기획 `{SCREEN}` 하나에 Figma 노드 여럿이 붙는 게 정상이다(위저드 단계 등).
  `mapping.yaml`의 `planning_screen ↔ figma_nodes[]` 로 표현한다.
- **프론트 세분화가 필요해도 스킬이 임의로 하위 식별자를 만들지 않는다.** `proposed_frontend_id`로
  **후보안**만 남기고, 최종 문서의 미해결 섹션에 "승인 대기"로 표시한다. 승인 시 `owner: frontend`로 승격.
- 프론트 식별자는 숫자 연장(`CRT-01-03`) 금지, **이름 기반**(`CRT/step-place`)만. 기획 소유 ID는 불변.

## 4. status 게이트

| status       | 최종 문서 본문(mermaid + 기능표) | 최종 문서 "미해결" 섹션 |
| ------------ | :------------------------------: | :---------------------: |
| `confirmed`  |             ✅ 반영              |            —            |
| `inferred`   |     ❌ (확정처럼 쓰지 않음)      |   ✅ 근거와 함께 노출   |
| `unresolved` |                ❌                |   ✅ 이유와 함께 노출   |

- **한쪽만 갱신된 상태를 숨기지 않는다.** 새 Figma 노드가 기획과 안 붙으면 `unresolved`,
  기획에만 있고 Figma에 없는 기능은 화면 흐름 노드로 만들지 않고 **기능표/보충 섹션**에만 둔다.

## 5. 보존 규칙 (축약 금지 — 이 문서는 하위 스킬의 SoT)

이 병합 문서는 `feature-planner` · `test-scenarios` · `tdd-*` 가 **인용하는 상위 SoT**다.
따라서:

- **모든 F 기능을 동등하게 보존한다.** 화면 전환을 일으키지 않는 기능(스플래시·인디케이터·개수제한 등)도
  테스트 대상이므로 축약·생략하지 않는다. mermaid 노드로 안 그리는 것은 **가독성 결정**일 뿐 중요도 판단이 아니다.
- **`구분`(회원/비회원/게스트)을 반드시 보존한다.** 인증 경계·접근 제어 테스트의 근거다.
  값이 없으면 `미확인`으로 표기하고 임의로 채우지 않는다.
- **설명을 요약·생략하지 않는다.** 하위 스킬이 이 문서만 보고 모호함 없이 작업할 수 있어야 한다.
  (파일럿 합격 기준: "이 문서만 보고 기능 문서/테스트 케이스를 모호함 없이 작성할 수 있는가")

### 하지 말 것 (경계 유지)

- 소비자 스킬을 위해 **필드를 미리 만들지 않는다** — 라우트 경로, 컴포넌트명, 테스트 케이스,
  인증 정책 판단 등 파생 정보는 이 문서 범위 밖이다. 이 문서는 "무엇이 있는가"까지만 담는다.

## 6. 최종 문서 구조 (2층)

최종 SoT는 `docs/design-system/user-flow/`에 두며 **merge 모드에서만 생성·수정한다.** Figma-only
또는 planning-only Markdown을 최종 폴더에 병렬로 두지 않는다. 최종 Markdown은 snapshot과
mapping의 파생물이므로 직접 편집하지 않는다.

모든 세부 기능을 mermaid 노드로 만들면 플로우가 다시 복잡해진다. **전환은 그림, 세부는 표**로 나눈다.

1. **화면 흐름 (mermaid)** — [`render-conventions.md`](./render-conventions.md)의 6노드·classDef·레이아웃 규약.
   - 노드 텍스트에 화면 식별자 병기(예: `모임 생성<br/>CRT`).
   - **전환을 일으키는 기능만** edge 라벨에 식별자로 병기(예: `건너뛰기 · ONB-01-F04`).
   - `confirmed` 매핑만 그린다.
2. **화면별 기능 (표)** — 모든 F 보존. 컬럼:
   `화면 | 화면 식별자 | 구분 | 기능 식별자 | 기능 | 설명 | Figma 반영 | owner`
   - `Figma 반영`: `노드/엣지 있음` vs `화면 내부 기능(노드 없음)`.
3. **미해결 (unresolved / inferred)** — status 게이트에서 본문 제외된 항목을 이유와 함께. 승인 대기 후보안 포함.

## 7. 신선도 헤더 (출처별)

mermaid 블록 맨 위 `%%` 주석에 기존 출처/신선도 헤더를 쓰되, **날짜를 출처별로 분리**한다.

```
%% ── 출처/신선도 (Source & Freshness) ──
%% 정본: Figma User Flow — <node-id 포함 링크>  |  기획 — <문서 경로>
%% Figma 동기화: <YYYY-MM-DD>  ·  기획 동기화: <YYYY-MM-DD>  ·  병합 생성: <YYYY-MM-DD>
%% 생성 스킬: user-flow-diagram(merge) · 규칙 기준일 <YYYY-MM-DD>
%% ⚠ 화면·흐름 정본=Figma, 식별자·기능 정본=기획 문서. 이 문서는 파생본이며 최신은 각 정본을 확인.
```

- 가짜 버전 숫자를 만들지 않는다. Figma는 node-id + 스냅샷 날짜로 시점 고정.
- 세 날짜가 어긋나면(한쪽만 최신) 그대로 드러낸다 — 숨기지 않는 게 이 헤더의 목적이다.
