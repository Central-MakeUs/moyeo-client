# PR Writer

현재 브랜치에서 한 일을 **moyeo 표준 PR 문서**로 옮긴다. 브랜치 이름에서 이슈 번호를,
커밋 이력에서 변경 내용을 뽑아 정해진 구조/톤으로 초안을 쓰고, **검토 게이트**를 지난 뒤
사용자 선택에 따라 `gh`로 바로 올리거나 로컬 파일로만 저장한다.

```
현재 브랜치 + 커밋 이력 + (연결된 이슈)
    ↓ 1단계 — 컨텍스트 수집 (이슈번호·커밋·diff)
    ↓ 2단계 — PR 본문 초안 (표준 구조/톤)
    ↓ [GATE] 초안 검토·승인
    ↓ 3단계 — 처리 방식 선택 (gh 바로 올리기 / 로컬 저장)
gh PR URL  또는  .local-docs/pr/pr-#N.md
```

**이 스킬이 하지 않는 것**: 커밋 생성·수정, 코드 변경, 브랜치 강제 push(사용자 승인 없이),
완료되지 않은 작업을 완료된 것처럼 서술. PR **본문 작성과 등록**까지만 책임진다.

---

## 1단계: 컨텍스트 수집

초안을 쓰기 전에 근거를 모은다. 추측하지 말고 git에서 사실을 읽는다.

### 이슈 번호 추출

```bash
git branch --show-current
```

브랜치 네이밍은 `type/#이슈번호/설명` (예: `feat/#31/customize-calendar`, `chore/#32/naming`)이다.
`type/` 뒤의 **첫 `#?숫자` 그룹**이 이슈 번호다 — `#`가 있든 없든(`feat/31/...`도) 숫자만 취한다.

- 추출되면 그 번호를 `Closes #N`과 파일명에 쓴다.
- `main`/`develop`이거나 숫자를 못 찾으면 **멈추고 사용자에게 이슈 번호를 묻는다**. 임의로 지어내지 않는다.

### 베이스 브랜치와 커밋 범위

moyeo 머지 흐름은 `feat/*` → **`develop`**이다. 베이스는 기본 `develop`.

```bash
# 이 브랜치가 develop에서 갈라진 뒤의 커밋들
git log --oneline develop..HEAD
git diff --stat develop...HEAD
```

- `develop`이 로컬에 없으면 `origin/develop`, 그것도 없으면 `main`으로 폴백하고 그 사실을 사용자에게 알린다.
- 커밋 메시지(Conventional Commits)와 diff stat으로 **무엇이/왜 바뀌었는지** 파악한다.
  `docs:`·`chore:` 같은 부수 커밋과 실제 기능 커밋을 구분한다.

### 연결 문서·이슈 (있으면)

- `gh issue view N`으로 이슈 본문·완료 조건(AC)을 읽는다(가능할 때). 없으면 건너뛴다.
- `docs/features/**/issue-*.md`, `docs/features/**/issues.md` 등 기획/시나리오 문서가 있으면 참고해
  "완료 조건"과 "작업 범위"의 근거로 삼는다.
- **커밋과 문서가 어긋나면 커밋(실제로 한 일)이 우선**이다. 문서에만 있고 커밋엔 없는 범위는
  "별도 이슈"로 분리해 서술한다(완료된 것처럼 쓰지 않는다).

## 2단계: PR 본문 초안

`references/pr-template.md`의 **구조와 톤**을 그대로 따른다. (원본 예시: moyeo Drawer PR)
템플릿을 처음 쓸 때 한 번 읽고, 아래 골격을 커밋 근거로 채운다.

```markdown
## 이슈

Closes #N

## 작업 배경

<왜 이 작업을 했는가 — 기존 문제 → 이번 접근. 2~3문단, 격식체.>

## 기존 시스템 대비 변경

| 구분 | 기존 | 변경 |
| ---- | ---- | ---- |
| ...  | ...  | ...  |

## <핵심 구조/사용법> # 컴포넌트면 사용 예시 코드블록 + 각 부분 책임

## <추가 설계 포인트> # 필요한 만큼 (레이아웃·상태·정책 등)

## 작업 범위

- <영역>
  - <세부 변경>

## 완료 조건

- [x] <검증된 사용자 대면 동작>
- [ ] PR 머지 # 아직 안 된 것은 정직하게 [ ]

## 검증

​`bash
<실제로 돌아가는 명령>
​`
확인 결과:

- [x] ...

## 리뷰 포인트

- <리뷰어가 판단해줬으면 하는 결정들>

## 기타

- <범위 밖·후속·한계>
```

### 톤·작성 원칙

- **격식체(~합니다/했습니다)**, 구조적. 표·코드블록·디렉터리 트리를 적극 활용한다.
- **커밋으로 검증되는 것만 완료(`[x]`)로**. 안 끝난 것(화면 주입, PR 머지 등)은 `[ ]`로 남긴다.
  없는 성과를 지어내는 것은 PR 신뢰를 무너뜨린다.
- "기존 시스템 대비 변경" 표는 이 문서의 핵심이다 — 리뷰어가 diff를 안 봐도 무엇이 달라졌는지
  한눈에 알게 한다. 커밋/파일 변화에서 3~7행을 뽑는다.
- **검증 섹션의 명령은 이 레포에서 실제 도는 것**만 쓴다(`CLAUDE.md` Commands 기준):
  `pnpm --filter @repo/web check-types`, `pnpm --filter @repo/web exec vitest run --project unit <경로>`,
  변경 파일 대상 `pnpm exec eslint --max-warnings 0 ...`, `git diff --check`. 안 돌려본 명령을 "통과"로 적지 않는다.
- PR **제목**도 함께 제안한다: `[type] 한 줄 요약` (한글, 이슈 제목/주요 커밋 테마 기반).

---

## [GATE] 초안 검토

완성한 **제목 + 본문 초안을 사용자에게 보여주고 검토·승인을 받는다.**

```
[GATE] 사용자가 초안을 승인(또는 수정 요청 반영)할 때까지 3단계로 넘어가지 않는다.
```

PR은 팀에게 공개되는 산출물이라, 틀린 서술이나 과장된 완료 표시가 그대로 나가면 안 된다.
사용자가 고쳐달라고 하면 반영 후 다시 보여준다.

---

## 3단계: 처리 방식 선택

승인된 초안을 어떻게 처리할지 **`AskUserQuestion`으로 명시적으로 선택받는다.**
(바로 올리는 것은 외부 공개 행위라 사용자 결정 없이 자동 실행하지 않는다.)

질문 예: "PR을 어떻게 처리할까요?"

- **옵션 A — gh CLI로 바로 PR 올리기**
- **옵션 B — 로컬 파일로만 저장** (`.local-docs/pr/pr-#N.md`)

### 옵션 A: gh로 등록

1. `gh`가 설치·인증돼 있는지 확인: `gh auth status` (실패하면 사용자에게 `gh auth login` 안내 후 옵션 B로 폴백 제안).
2. 브랜치가 원격에 없으면 push: `git push -u origin <현재브랜치>`.
   - **`main`/`develop`에 직접 push 금지** (moyeo 규칙). 반드시 feature 브랜치에서만.
3. 본문을 임시 파일로 쓰고 등록:
   ```bash
   gh pr create --base develop --head <현재브랜치> \
     --title "<제안 제목>" --body-file <임시파일>
   ```
4. 반환된 PR URL을 사용자에게 전달한다. (임시 파일은 정리)

### 옵션 B: 로컬 저장

```
.local-docs/pr/pr-#<이슈번호>.md
```

- `.local-docs/`는 gitignore돼 있어(스크래치) 실수 커밋 걱정이 없다. `pr/` 하위 폴더로 모아 정리한다.
- 폴더가 없으면 만든다. 파일이 이미 있으면 덮어쓸지 사용자에게 확인한다.
- 저장 경로를 사용자에게 알리고, 나중에 옵션 A로 올릴 수 있음을 덧붙인다.

## 요약 체크리스트

- [ ] `git branch --show-current`로 이슈 번호를 추출했는가 (못 찾으면 물었는가)
- [ ] `develop..HEAD` 커밋·diff로 실제 변경을 파악했는가
- [ ] 커밋으로 검증되는 것만 `[x]`로 표기했는가 (미완은 `[ ]`)
- [ ] 검증 섹션에 실제 도는 명령만 적었는가
- [ ] 초안을 보여주고 **승인**받았는가 (GATE)
- [ ] gh 등록 / 로컬 저장을 **사용자에게 선택**받았는가
- [ ] 커밋·코드를 건드리지 않았는가 (이 스킬은 PR 본문·등록만)
