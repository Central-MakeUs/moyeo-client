# PR Writer

완료된 브랜치의 변경을 `.github/PULL_REQUEST_TEMPLATE.md` 구조에 맞는 PR 제목과 본문으로 정리한다.
추측하거나 완료 여부를 과장하지 않고, Git과 이슈에서 확인한 사실만 사용한다.

```text
브랜치·커밋·diff·이슈 수집
  → 템플릿에 맞춰 제목·본문 초안 작성
  → [GATE] 사용자 검토 및 승인
  → gh로 PR 등록 또는 .local-docs에 저장
```

이 스킬은 코드·커밋을 수정하거나, 승인 없이 push 또는 PR 등록을 하지 않는다.

## 1. 근거 수집

### 브랜치와 이슈 번호

```bash
git branch --show-current
```

- `type/#N/설명` 또는 `type/N/설명`에서 `type/` 뒤 첫 숫자를 이슈 번호로 사용한다.
- 번호를 찾지 못하면 임의로 만들지 말고 사용자에게 묻는다.
- `main`이나 `develop`에서는 PR 작성을 진행하기 전에 대상 브랜치를 확인한다.

### 베이스와 변경 범위

기본 베이스는 `develop`이다. 로컬 `develop`이 없으면 `origin/develop`, 그마저 없으면 `main`을
사용하되 폴백 사실을 사용자에게 알린다.

```bash
git log --oneline develop..HEAD
git diff --stat develop...HEAD
git diff develop...HEAD
```

- Conventional Commit 제목뿐 아니라 실제 diff를 함께 확인한다.
- 현재 작업 트리의 미커밋 변경은 PR 범위와 구분한다.
- 여러 커밋이 서로 다른 목적이면 기능 변경과 문서·테스트·정리 작업을 나눠 서술한다.

### 이슈와 프로젝트 문서

- 가능하면 `gh issue view <번호>`로 이슈 본문, AC, 의존성을 확인한다.
- 관련 기획·설계 문서가 있으면 작업 배경과 AC의 근거로 사용한다.
- 문서와 코드가 다르면 실제 커밋과 diff를 우선한다.
- 구현되지 않은 요구사항은 완료로 적지 않고 `기타 · 후속`에 남긴다.

## 2. 초안 작성

먼저 `.github/PULL_REQUEST_TEMPLATE.md`를 처음부터 끝까지 읽는다. 이 파일이 PR 구조의
단일 기준이다.

- 헤딩과 표의 의미를 유지하면서 실제 변경 내용으로 채운다.
- 작성 안내용 HTML 주석과 빈 예시는 최종 본문에서 제거한다.
- 해당 없는 선택 섹션은 삭제하거나 템플릿 안내에 따라 `없음`으로 명시한다.
- 템플릿에 없는 고정 섹션을 임의로 추가하지 않는다. 구조 변경은 템플릿에서 먼저 한다.

### 작성 규칙

- 제목은 `type(scope): 한 줄 요약` 형식으로 제안한다.
- 본문은 격식체로 쓰고, 리뷰어가 diff를 전부 읽지 않아도 변경 이유와 구조를 이해하게 한다.
- 변경 유형은 커밋과 diff에 해당하는 항목만 선택한다.
- 이슈의 AC를 가져오되, 현재 PR에서 실제 달성한 항목만 `[x]`로 표시한다.
- 실행해 성공을 확인한 검증만 `[x]`로 표시한다. 실행하지 않았거나 실패한 검증은 `[ ]`로 둔다.
- `PR 머지`, 후속 구현 등 아직 일어나지 않은 작업은 항상 `[ ]`다.
- 의존성을 확인할 수 없으면 추측하지 않고 `의존성 없음` 또는 `확인 필요`로 표시한다.
- 테스트 실패나 알려진 제약은 숨기지 않고 `검증` 또는 `기타 · 후속`에 기록한다.

검증 명령은 저장소에 실제 존재하며 이번 변경에 맞는 것만 선택한다. 예:

```bash
pnpm --filter @repo/web check-types
pnpm --filter @repo/web exec vitest run --project unit <변경 경로>
pnpm exec eslint --max-warnings 0 <변경 파일>
git diff --check
```

## 3. [GATE] 사용자 검토

제안 제목과 완성된 본문 전체를 사용자에게 보여준다. 사용자가 승인하거나 수정 요청이 모두
반영되기 전에는 파일 저장, push, `gh pr create`를 실행하지 않는다.

수정 요청이 있으면 초안을 고쳐 다시 검토받는다.

## 4. 승인 후 처리

승인받은 뒤 다음 중 무엇을 원하는지 명시적으로 확인한다.

1. `gh`로 PR 등록
2. `.local-docs/pr/pr-#<이슈번호>.md`에 로컬 초안 저장

### gh로 등록

1. `gh auth status`로 설치와 인증을 확인한다.
2. 브랜치가 원격에 없다면 사용자 동의를 받은 뒤 해당 작업 브랜치만 push한다.
3. 임시 본문 파일을 사용해 등록한다.

```bash
gh pr create \
  --base develop \
  --head <현재 브랜치> \
  --title "<승인된 제목>" \
  --body-file <임시 본문 파일>
```

4. 생성된 PR URL을 전달하고 임시 파일을 정리한다.

`main` 또는 `develop`에 직접 push하지 않는다. 인증이나 등록에 실패하면 원인을 알리고 로컬
저장 방식을 제안한다.

### 로컬 저장

- `.local-docs/pr/`가 없으면 만든다.
- 같은 파일이 있으면 덮어쓰기 전에 사용자에게 확인한다.
- 저장 경로를 알리고, 이후 승인된 본문으로 PR을 등록할 수 있다고 안내한다.

## 완료 체크리스트

- [ ] 브랜치에서 이슈 번호를 확인했다.
- [ ] 베이스 브랜치와 비교 범위를 확인했다.
- [ ] 커밋, 전체 diff, 관련 이슈·문서를 확인했다.
- [ ] `.github/PULL_REQUEST_TEMPLATE.md`를 기준으로 작성했다.
- [ ] 검증된 항목만 `[x]`로 표시했다.
- [ ] 제목과 본문 전체를 사용자에게 보여주고 승인받았다.
- [ ] 승인 후 등록 또는 로컬 저장 방식을 선택받았다.
- [ ] 사용자 승인 없이 코드·커밋·원격 상태를 변경하지 않았다.
