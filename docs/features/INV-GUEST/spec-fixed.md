# INV-GUEST 게스트 모임 참여 — 확정 요구사항

> 단계 1 산출물. 원본 화면 명세는
> [`docs/fe-implement-spec/invite/guest-meeting-join/guest-meeting-join.md`](../../fe-implement-spec/invite/guest-meeting-join/guest-meeting-join.md).
> 이 문서는 그 명세의 `§9 확인 필요`를 인터뷰로 좁혀 **확정된 것만** 적는다.

---

## 1. 범위

로그인하지 않은 사용자가 초대 링크에서 `이번에만 게스트로 참여하기`를 골라, 모임용 닉네임과
숫자 4자리 비밀번호를 넣고 모임 유형에 맞는 참여 정보를 제출해 완료 화면까지 가는 흐름.

```
/i/{code}  →  /i/{code}/guest  →  [일정]  →  [출발지]  →  /i/{code}/complete
                                  planningType에 따라 생략
```

**회원 참여 흐름(`/i/{code}/nickname`)은 이번 범위가 아니다.** 일정·출발지 화면과 제출
파이프라인을 게스트로 먼저 완성한 뒤, 회원은 닉네임 화면과 `MemberJoinRequest`만 바꿔 재사용한다.

## 2. 용어 정의 (Ubiquitous Language)

| 용어           | 뜻                                                                         | 코드에서                 |
| -------------- | -------------------------------------------------------------------------- | ------------------------ |
| 초대 코드      | 초대 링크의 식별자. 화면 경로는 `inviteToken`, API는 `inviteCode`로 부른다 | `inviteCode`             |
| 모임용 닉네임  | 계정 기본 닉네임이 아니라 **그 모임 안에서만** 쓰는 표시 이름              | `nickname`               |
| 참여 비밀번호  | 게스트가 참여 정보를 확인할 때 쓸 숫자 4자리                               | `password`               |
| 후보 날짜      | 모임장이 정한 선택 가능한 날짜 목록. **참여자는 바꿀 수 없다**             | `scheduleCandidateDates` |
| 일정 응답      | 참여자가 고른 가능한 날짜 또는 시간 범위                                   | `scheduleResponse`       |
| 참여 초안      | 여러 화면을 거치는 동안 들고 있는 게스트 입력 묶음                         | `useGuestJoinDraft`      |
| 참여 입력 단계 | 진행 표시에 세는 화면. 신원·일정·출발지만 해당하고 완료 화면은 제외한다    | `step`                   |

## 3. 확정된 결정

### 3-1. 참여 초안은 메모리 전용 zustand 스토어에 둔다

`useGuestJoinDraft`를 신설하되 `persist`를 쓰지 않는다. 초안에 **참여 비밀번호가 들어가므로**
디스크에 남기지 않는 쪽을 택한다. 게스트 신원은 닉네임과 4자리뿐이라 재입력 부담이 작다.

새로고침하면 입력이 사라지고 신원 화면부터 다시 시작한다. 모임장 위저드(`useCreateMeetingDraft`)는
`persist`를 쓰므로 두 초안의 지속성 정책이 다르다는 점을 주석에 남긴다.

### 3-2. 초안이 `inviteToken`을 들고 다음 화면이 대조한다

메모리 전용이라 새 문서 로드에서는 초안이 비워진다. 다만 클라이언트 내비게이션으로 다른 초대
링크에 도달하면 메모리가 남아, **다른 모임에 잘못된 닉네임·일정이 제출될 수 있다.**

초안의 `identity`에 `inviteToken`을 함께 저장하고, 초안을 읽는 화면과 제출 시점에 현재 경로의
값과 대조한다. 다르거나 초안이 비어 있으면 신원 화면으로 돌려보낸다.

### 3-3. 무효한 일정 응답은 쓰기 시점에 정리한다

후보 날짜가 바뀌면 그 날짜에 매인 시간 범위는 **즉시** 스토어에서 사라져야 한다. 제출 직전에만
거르면 화면에는 무효한 선택이 남아 "골랐는데 안 갔다"가 되고, 셀렉터에서만 거르면 스토어에
쓰레기가 쌓인다.

게스트 흐름에서 후보 날짜를 바꾸는 주체는 게스트가 아니라 **모임장**이다. 그래서 정리를 부르는
지점은 "일정 화면이 서버에서 받은 후보 날짜를 스토어에 알려줄 때"다.

> 같은 정리 함수를 모임장 위저드의 알려진 버그(후보 날짜를 1~4일 → 1~3일로 줄여도 4일의 시간대가
> `scheduleResponse`에 남는 문제)에도 쓸 수 있게 순수 함수로 뺀다. 그 수정 자체는 이번 범위가 아니다.

### 3-4. 모임 설정은 각 라우트가 서버 컴포넌트로 받는다

`planningType`·`scheduleInputType`·후보 날짜·가능 시간은 각 참여 화면의 `page.tsx`가 서버에서
조회해 props로 내려준다. INV-01이 이미 쓰는 방식이다.

- 설정 로딩 스피너가 필요 없다. 화면이 그려질 때 값이 이미 있다.
- **매 단계가 서버의 최신 후보 날짜를 본다.** 모임장이 그새 바꿔도 같은 자리에서 걸러진다.
- 입력 화면이 props만 받으므로 테스트에 네트워크 모킹이 없다.

단계를 넘길 때 서버를 한 번 다녀오는 대기가 생긴다. 각 라우트에 `loading.tsx`를 둬서 메운다.

### 3-5. 진행 표시는 입력 화면만 센다

신원 화면을 첫 단계로 포함하고 완료 화면은 제외한다.

| `planningType`       | 단계                 | 총 단계 |
| -------------------- | -------------------- | ------- |
| `SCHEDULE_ONLY`      | 신원 → 일정          | 2       |
| `PLACE_ONLY`         | 신원 → 출발지        | 2       |
| `SCHEDULE_AND_PLACE` | 신원 → 일정 → 출발지 | 3       |

`scheduleInputType`은 단계 **수**를 바꾸지 않는다. 참여자의 일정 화면은 `DATE_ONLY`면 캘린더,
`DATE_AND_TIME`이면 시간표로 **내용만** 달라진다. 모임장만 날짜·시간 두 화면을 거친다(INV-02).

### 3-6. 제출 실패는 제자리에서 알린다

`POST .../guests`가 실패하면 화면과 입력값을 그대로 두고 토스트로 사유를 알리며 버튼을 다시
활성화한다. 마감·정원 초과처럼 재시도해도 안 되는 사유는 문구만 다르게 한다.

연속 탭에도 요청은 한 번만 나가야 한다.

## 4. 입력 규칙 (API 계약 그대로)

| 값       | 규칙                    | 근거                        |
| -------- | ----------------------- | --------------------------- |
| 닉네임   | `^[가-힣A-Za-z]{2,10}$` | `GuestJoinRequest.nickname` |
| 비밀번호 | `^[0-9]{4}$`            | `GuestJoinRequest.password` |

비밀번호는 기본 마스킹이고 눈 아이콘으로 전환하며, 전환해도 입력값과 커서를 유지한다.

## 5. 여전히 확인이 필요한 것

구현을 막지는 않지만 확정되면 문서를 갱신한다.

1. **후속 Figma 화면** — 게스트 신원 화면 이미지는 첨부됐다. 일정·출발지 화면과
   `planningType`별 진행 표시 변형은 토큰과 기존 컴포넌트로 최소 구현하고 시안이 오면 맞춘다.
2. **비밀번호 용도 안내 문구** — 무엇에 쓰는 비밀번호인지, 잊었을 때 어떻게 되는지 알려줄 문구가
   없다. 서버도 재입장·수정 검증을 아직 구현하지 않았다.
3. **닉네임 오류 문구와 노출 시점** — 기존 온보딩 닉네임 화면 정책을 따를지 확인이 필요하다.
4. **제출 실패 사유별 문구** — 닉네임 중복·마감·정원 초과·네트워크 오류의 서버 응답 계약이
   문서화돼 있지 않다.
5. **완료 화면(INV-04) 정책** — 뒤로가기·이탈 동작이 정해져 있지 않다. 이번 범위는 완료 화면으로
   이동하는 것까지다.
