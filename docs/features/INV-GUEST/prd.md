# INV-GUEST 게스트 모임 참여 — PRD

> 단계 2 산출물. 확정 요구사항은 [`spec-fixed.md`](./spec-fixed.md), 화면 SoT는
> [`guest-meeting-join.md`](../../fe-implement-spec/invite/guest-meeting-join/guest-meeting-join.md).
> **이 기능에 대해 궁금하면 이 문서만 보면 된다**가 목표다.

---

## 1. 개요

로그인하지 않은 사용자가 초대 링크에서 게스트로 모임에 참여한다. 모임용 닉네임과 숫자 4자리
비밀번호를 넣고, 모임 유형에 필요한 일정 또는 출발지를 입력한 뒤 한 번의 요청으로 참여를
확정한다.

INV-01이 열어둔 `이번에만 게스트로 참여하기` 뒤의 참여 흐름을 채운다. Issue 1에서 게스트 신원
입력을 구현하고, 후속 이슈에서 일정·출발지와 제출 흐름을 완성한다.

```
/i/{code}  →  /i/{code}/guest  →  [일정]  →  [출발지]  →  /i/{code}/complete
                                  planningType에 따라 생략
```

## 2. 사용자 스토리

- 링크를 받은 사람으로서, 계정을 만들지 않고도 모임에 참여하고 싶다.
- 참여자로서, 내 계정 닉네임 대신 이 모임에서 쓸 이름을 정하고 싶다.
- 참여자로서, 여러 화면을 오가는 동안 앞서 입력한 값이 사라지지 않았으면 한다.
- 참여자로서, 내가 고른 일정이 실제로 제출되는지 확신하고 싶다 — 화면에 보이는 선택과 서버에
  보내는 값이 달라선 안 된다.
- 참여자로서, 제출이 실패해도 처음부터 다시 입력하고 싶지 않다.

## 3. 기술 결정 (ADR)

### ADR-1. 참여 초안을 메모리 전용 zustand 스토어에 둔다

**Context**
게스트는 신원·일정·출발지를 서로 다른 라우트에서 입력하고 **마지막에 한 번** 제출한다
(`GuestJoinRequest`가 셋을 한 번에 받는다). 그동안 값을 어딘가 들고 있어야 한다.
그 값에는 **참여 비밀번호**가 포함된다.

**Decision**
`features/meeting/invite-participation/model/guest-join-draft.ts`에 zustand 스토어를 만들되
`persist`를 **쓰지 않는다.** 초안은 `identity` 하나로 묶고 `inviteToken`을 함께 담아, 다음 화면이
"이 초안이 지금 모임 것인가"를 검증할 수 있게 한다.

**Alternatives**

- **zustand + `persist`** — 새로고침·앱 전환에도 입력이 남아 이탈이 줄지만, **비밀번호가
  스토리지에 평문으로 남는다.** 게스트 신원은 닉네임과 4자리뿐이라 재입력 부담이 작은 반면,
  비밀번호를 디스크에 남기는 대가는 되돌리기 어렵다. 거부.
- **단일 라우트에서 단계 전환** — 스토어가 필요 없지만 화면 SoT가 정한 라우트 구조를 뒤집고,
  뒤로가기가 브라우저 히스토리와 어긋난다. 거부.

**Consequences**

- (+) 비밀번호가 디스크에 남지 않는다.
- (+) 새 문서 로드마다 초안이 비워지므로 **다른 모임의 입력이 따라오는 사고가 구조적으로
  거의 사라진다**(ADR-2 참고).
- (−) 새로고침하면 입력이 사라진다. 사용자는 신원 화면부터 다시 시작해야 한다.
- (−) 모임장 위저드(`useCreateMeetingDraft`, persist)와 지속성 정책이 달라진다. 두 초안의
  성격이 다르다는 것을 주석으로 남긴다.

### ADR-2. 초안이 `inviteToken`을 들고 다음 화면이 검증한다

**Context**
초안이 지금 보고 있는 모임의 것이 아닐 수 있다. 클라이언트 내비게이션으로 다른 초대 링크에
도달하면 메모리가 유지되기 때문이다. 게스트는 로그인 상태가 없어 사용자 단위로도 못 가른다.

**Decision**
`identity`에 `inviteToken`을 함께 저장한다. 일정·출발지 화면과 제출 시점에 현재 경로의
`inviteToken`과 대조해, 다르면 초안을 쓰지 않고 신원 화면으로 돌려보낸다.

ADR-1이 메모리 전용이므로 **새 문서 로드에서는 이 검증이 필요 없다.** 클라이언트 내비게이션
경로만 방어하면 된다.

**Alternatives**

- **진입 화면에서 코드가 다르면 스토어를 비운다(`ensureFor`)** — persist를 전제한 설계다.
  메모리 전용에서는 비울 것이 애초에 남아 있지 않은 경우가 대부분이라 과하다. 거부.
- **검증하지 않는다** — 대부분의 경로에서 문제가 없지만, 초안이 남은 채 다른 모임으로 이동하면
  **다른 모임에 잘못된 닉네임·일정이 제출된다.** 조용히 틀리는 종류라 거부.

**Consequences**

- (+) 잘못된 초안이 제출되는 경로가 막힌다.
- (+) 검증이 순수 비교라 테스트가 쉽다.
- (−) 초안을 읽는 화면마다 대조가 필요하다. 빠뜨리면 다시 샌다 — 초안을 읽는 진입점을
  한 곳(훅 또는 셀렉터)으로 모아 빠뜨릴 자리를 줄인다.

### ADR-3. 모임 설정은 각 라우트가 서버 컴포넌트로 받아 props로 내린다

**Context**
일정·출발지 화면은 `planningType`·`scheduleInputType`·후보 날짜·가능 시간이 있어야 그릴 수
있다. 이 값들은 서버가 소유하고 **모임장이 언제든 바꿀 수 있다.**

**Decision**
각 참여 라우트의 `page.tsx`를 서버 컴포넌트로 두고 `fetchInvitationForPage`로 조회해 입력
화면에 props로 내린다. INV-01이 이미 쓰는 방식이다. 단계 이동 대기는 `loading.tsx`로 메운다.

**Alternatives**

- **클라이언트에서 TanStack Query 조회** — 단계 이동이 캐시 적중으로 즉시지만, 화면마다
  로딩·오류 분기가 생기고 스켈레톤 시안이 없어 디자인을 발명하게 된다. 거부.
- **신원 화면에서 한 번 조회해 스토어에 스냅샷** — 요청이 한 번뿐이라 가볍지만, 모임장이 그새
  후보 날짜를 바꿔도 **제출 직전까지 모른다.** 이 기능의 핵심 위험을 방치하므로 거부.

**Consequences**

- (+) 설정 로딩 스피너가 필요 없다. 화면이 그려질 때 값이 이미 있다.
- (+) 매 단계가 서버의 최신 후보 날짜를 본다.
- (+) 입력 화면이 props만 받으므로 테스트에 네트워크 모킹이 없다.
- (−) 단계를 넘길 때 서버를 한 번 다녀온다. `loading.tsx`가 없으면 멈춘 것처럼 보인다.
- (−) `revalidate: 60` 때문에 최대 60초 낡은 설정을 볼 수 있다.

### ADR-4. 후보 날짜를 받는 시점에 무효한 일정 응답을 정리한다

**Context**
`scheduleResponse.availableTimeRanges[].candidateDate`는 후보 날짜에 매여 있다. 후보에서 빠진
날짜의 시간 범위가 남으면 **서버 제출에서 에러가 난다.** 모임장 위저드에 같은 성격의 알려진
버그가 있다(후보 날짜를 1~4일 → 1~3일로 줄여도 4일의 시간 범위가 남는다).

게스트는 후보 날짜를 **바꿀 수 없다.** 그래서 무효값이 생기는 경로는 둘뿐이다 —
① 다른 `inviteCode`로 진입(ADR-2가 처리) ② 모임장이 후보 날짜를 변경.

**Decision**
스토어에 `syncCandidateDates(dates)` 액션을 두고, 일정 화면이 SSR로 받은 후보 날짜로 이것을
호출한다. 액션은 `scheduleResponse`에서 후보에 없는 날짜의 항목을 즉시 걸러낸다.
거르는 로직은 순수 함수 `pruneScheduleResponse(response, candidateDates)`로 분리한다.

**Alternatives**

- **제출 직전에만 거른다** — 변경이 한 곳에 모여 가장 작지만, 화면에는 무효한 선택이 남아
  "골랐는데 안 갔다"가 된다. 스토어와 화면이 어긋난다. 거부.
- **셀렉터에서 읽을 때만 거른다** — 화면과 제출이 항상 일치하지만 스토어에 쓰레기가 계속 쌓이고,
  셀렉터를 안 거치는 경로가 하나만 생겨도 다시 샌다. 거부.

**Consequences**

- (+) 스토어에 무효값이 존재하는 순간이 없다. 이후 모든 화면·제출이 자동으로 안전하다.
- (+) `pruneScheduleResponse`를 모임장 버그 수정에도 그대로 쓸 수 있다.
- (−) 사용자가 고른 선택이 **말없이 사라진다.** 모임장이 후보를 바꾼 경우 안내가 필요할 수
  있으나 문구가 확정되지 않아 이번엔 조용히 정리만 한다.

### ADR-5. 시간표 ↔ DTO 변환만 `shared`로 내리고, 스텝 배선은 슬라이스마다 둔다

**Context**
모임장의 `schedule-times-step`·`departure-step`을 게스트가 그대로 쓰고 싶지만
**steiger가 같은 레이어 슬라이스 간 import를 막는다**(`fsd/forbidden-imports`, 실측 확인).
중립 슬라이스를 하나 더 만들어도 features→features라 똑같이 막힌다. 공유하려면 `entities`나
`shared`로 내려야 한다.

한편 무거운 UI(드래그 시간표·드래그 캘린더)는 **이미 `shared/ui`에 있다.** 슬라이스에 남은
것은 스토어를 읽고 쓰는 배선 100줄 안팎과, 셀 키 ↔ `ScheduleAvailabilityRequest` 변환이다.

**Decision**
`to-availability-time-ranges`·`from-availability-time-ranges`·`build-past-cell-keys`를
`shared/ui/time-grid`로 옮긴다. 이미 그 폴더에 같은 성격의 순수 함수들이 있고, 이 함수들은
`parseCellKey`와 `shared/api` 타입만 쓰므로 도메인 의존이 없다.

스텝 배선(`schedule-times-step` 등)은 옮기지 않는다. 게스트는 자기 스토어에 맞는 배선을
새로 만든다.

**Alternatives**

- **전면 공용화(스텝까지 `entities`/`shared`로 이동)** — 중복이 완전히 사라지지만 파일 이동
  diff가 커져 리뷰가 어렵고, 모임장 흐름 회귀 위험이 함께 온다. 소비처가 셋(모임장·게스트·회원)이
  된 뒤에 해도 늦지 않다. 거부.
- **전면 중복(변환 함수까지 게스트가 새로 작성)** — 모임장 코드를 전혀 안 건드려 가장 안전해
  보이지만, 변환 함수는 **서버 계약과 직결**돼 두 벌이면 반드시 어긋난다. 게다가 모임장의 알려진
  잔존값 버그가 이 변환 주변이라 한쪽만 고치는 사고가 실제로 일어난다. 거부.

**Consequences**

- (+) 계약과 직결된 코드가 한 벌로 유지된다.
- (+) 모임장 쪽 변경이 import 경로 수정에 그쳐 회귀 위험이 작다.
- (−) 스텝 배선은 여전히 두 벌이다. 회원 흐름까지 오면 세 벌이 된다.
- (−) `departure-search-step`(장소 검색·모달 라우팅)은 옮기지 않아, 게스트 출발지 화면에서
  필요해지면 그때 다시 판단해야 한다.

## 4. Out of Scope

이번에 **하지 않는 것**을 명시한다.

- **회원 참여 흐름**(`/i/{code}/nickname`, `MemberJoinRequest`) — 다음 이슈. 일정·출발지 화면과
  제출 파이프라인을 게스트로 먼저 완성한 뒤 닉네임 화면과 DTO만 바꿔 재사용한다.
- **모임장 위저드의 잔존값 버그 수정** — `pruneScheduleResponse`를 재사용 가능한 형태로 만들되,
  모임장 흐름에 적용하는 것은 별도 작업이다.
- **참여 완료 화면(INV-04)의 내용·뒤로가기 정책** — 이번 범위는 완료 경로로 **이동**하는 것까지다.
- **게스트 재입장·참여 정보 수정** — 서버가 비밀번호 검증 정책을 아직 구현하지 않았다.
- **장소 검색 화면의 게스트 이관** — 출발지 입력에서 검색이 필요해지면 그때 판단한다.
- **제출 실패 사유별 분기 문구** — 서버 오류 코드 계약이 문서화되지 않았다. 공통 토스트 문구로
  시작한다.
- **진행 표시의 시각 형태** — 게스트 신원 화면 이미지는 첨부됐지만 `planningType`별 진행률 변형은
  미첨부다. 단계 수 계산 로직만 확정하고 표현은 기존 토큰·컴포넌트로 최소 구현한다.
- **`departure-search-step`·`departure-radio-group`의 공용화** — ADR-5 참고.
