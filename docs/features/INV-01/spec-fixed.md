## 0. 사이클 스코프

INV-01은 **초대 링크로 들어온 사용자를 참여 입력 화면 입구까지 보내는 것**으로 완결한다.
링크가 어떤 경로로 도착했는지(앱/웹)와 그 다음 참여 입력은 이번 범위가 아니다.

| 구분            | 범위                                                                   |
| --------------- | ---------------------------------------------------------------------- |
| **이번 사이클** | `/i/[inviteToken]` 화면 — 초대 조회·상태 분기·안내 문구·모임 정보 표시 |
|                 | 참여하기 → 로그인 Drawer(비로그인) 또는 모임 닉네임 화면(로그인) 이동  |
|                 | 로그인 왕복 시 초대 링크 복귀 계약 (온보딩 경유 포함)                  |
|                 | 조회 로딩·404·오류 상태 화면                                           |
| **다음 사이클** | 딥링크(Universal Link · App Link · 카카오 앱 실행) — 별도 feature      |
|                 | VIEW-01 모임 현황 화면 (`/meetings/[meetingId]`)                       |
|                 | `/i/{code}/nickname` · `/guest` 이후의 참여 입력 화면들                |

## 1. 확정 근거 (2026-07-31 인터뷰)

`inv-01.md` §9의 8개 항목에 대응한다.

| #   | §9 항목               | 결정                                                 | 근거                                                                                                                                                                               |
| --- | --------------------- | ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | §9-1 F03 범위 축소    | **모임장 닉네임만 표시로 확정**                      | 최신 시안·`MeetingInvitationResponse`·스펙 본문이 3자 일치. 참여자 목록과 `[모임장]` 표기는 API에도 없다                                                                           |
| 2   | §9-5·§9-7 딥링크      | **별도 feature로 분리**                              | `app.json`에 `associatedDomains`(iOS)·`intentFilters`(Android)가 없어 현재 링크는 앱을 열 수 없다. 켜려면 네이티브 재빌드가 필요해 OTA로 못 나간다 (§7-1 참고)                     |
| 3   | §9-7 Drawer 구성 기준 | **`isNativeContext()`** — 앱 안=`member`, 웹=`guest` | 웹에서 "앱 설치 여부"는 신뢰성 있게 판별할 수 없지만 "WebView 안인지"는 확실하다. 앱 안에서 들어온 사용자는 앱 설치가 자명하므로 시안 2장의 의도와 일치한다                        |
| 4   | §9-2 조회 상태        | **App Router 상태 파일 분리**                        | 스펙 §9-2가 이미 권장한 방식. `generateMetadata`의 OG용 조회와 데이터를 공유해 이중 호출이 없고, 초기 렌더에 데이터가 있어 카드 스켈레톤이 사실상 불필요하다                       |
| 5   | §9-3 참여 분기        | **회원 → `/nickname`, 게스트 → `/guest`**            | `MemberJoinRequest.nickname`이 required이고 "회원 기본 닉네임과 다르게 입력할 수 있습니다"라고 명시. 모임 닉네임은 **모임마다 항상 필요**하므로 "필요 여부 판별"이라는 문제가 없다 |
| 6   | §9-4 복귀 경로        | **`SocialLoginButtons`에 `next` prop 추가**          | 공유된 URL에 쿼리를 덧붙이지 않는다. 기존 `/login` 호출부는 `useSearchParams` 기본 동작 그대로 둔다                                                                                |
| 7   | §9-4 온보딩 왕복      | **이번 범위에 포함**                                 | 초대 링크로 들어온 신규 가입자가 가장 흔한 유입 경로다. 여기서 초대장을 잃으면 유입이 통째로 샌다                                                                                  |
| 8   | §9-6 진행상황 버튼    | **UI만 그리고 비활성**                               | `/meetings/[meetingId]` 라우트도 VIEW-01 기획 문서도 없다. 스펙 §7 F05의 "잘못된 경로를 만들지 않는다"를 목적지 미구현까지 확장 적용한다                                           |
| 9   | §9-8 미첨부 시안      | **§7 F02 문구를 구현 기준으로 사용**                 | 정원 초과·기한 경과 화면 이미지는 없지만 문구는 확정돼 있다                                                                                                                        |

### 서버 계약 확인 결과

`ParticipationStatusResponseReason` = `AVAILABLE | DEADLINE_PASSED | PARTICIPANT_LIMIT_EXCEEDED`.
서버 스키마 주석이 "기한과 정원이 모두 막힌 경우 기한 초과를 우선 반환합니다"라고 명시하므로,
스펙 §7 F01의 우선순위 규칙은 **프론트에서 다시 계산하지 않고 서버 값을 그대로 쓰면 된다**.

## 2. 용어 정의 (Ubiquitous Language)

코드·문서·대화에서 아래 단어가 항상 같은 것을 가리킨다.

| 용어               | 정의                                                                        | 서버 필드 · 코드             |
| ------------------ | --------------------------------------------------------------------------- | ---------------------------- |
| **초대 코드**      | 초대 링크를 식별하는 값. 경로 파라미터 이름은 `inviteToken`이지만 값은 이것 | `inviteCode`                 |
| **참여 가능 상태** | 서버가 계산한 참여 허용 여부와 사유. 프론트가 재계산하지 않는다             | `participationStatus`        |
| **서비스 닉네임**  | 계정에 한 번 설정하는 닉네임. 온보딩(`/nickname`)에서 정한다                | `SessionViewer.nickname`     |
| **모임 닉네임**    | 모임 안에서만 쓰는 표시 이름. **모임마다 매번 입력**한다                    | `MemberJoinRequest.nickname` |
| **회원 참여**      | 로그인 사용자로 참여. 모임 닉네임만 입력                                    | `POST joinMember`            |
| **게스트 참여**    | 비로그인으로 참여. 모임 닉네임 + 비밀번호 입력                              | `POST joinGuest`             |
| **로그인 Drawer**  | 참여하기를 탭한 비로그인 사용자에게 뜨는 바텀시트                           | `widgets/login-drawer`       |

> ⚠️ **서비스 닉네임과 모임 닉네임을 구분하라.** 경로가 `/nickname`(서비스 온보딩)과
> `/i/{code}/nickname`(모임 닉네임)으로 이름이 겹쳐 혼동하기 쉽다.

## 4. 상태별 동작

### 4-1. 초대 조회 상태

| 상태        | 처리                                     | 담당 파일                           |
| ----------- | ---------------------------------------- | ----------------------------------- |
| 조회 중     | 로딩 화면. 참여하기 비활성               | `loading.tsx`                       |
| 404         | 유효하지 않은 초대 안내 + 이탈 수단      | `not-found.tsx` (`notFound()` 호출) |
| 404 외 실패 | 실패 안내 + `reset()` 재시도 + 이탈 수단 | `error.tsx` (throw)                 |
| 성공        | 모임 정보 렌더                           | `page.tsx` → `InviteLandingPage`    |

### 4-2. 참여 가능 상태 (`participationStatus`)

| `reason`                     | 참여하기 | PageHeader title        | PageHeader description                   |
| ---------------------------- | -------- | ----------------------- | ---------------------------------------- |
| `AVAILABLE` (`canJoin=true`) | 활성     | 모임 초대장이 왔어요!   | 모임에 참여해서 일정과 장소를 정해보세요 |
| `DEADLINE_PASSED`            | 비활성   | 마감 기한이 지났어요    | 아쉽지만 현재는 더 이상 참여할 수 없어요 |
| `PARTICIPANT_LIMIT_EXCEEDED` | 비활성   | 모임 인원이 모두 찼어요 | 아쉽지만 현재는 더 이상 참여할 수 없어요 |
| 필드 자체가 없음             | 비활성   | (기본 문구 유지)        | —                                        |

- 서버의 `participationStatus.message`보다 위 `reason` 대응 문구를 우선한다.
- 두 사유가 동시에 성립하면 서버가 `DEADLINE_PASSED`를 반환하므로 프론트 우선순위 로직은 없다.

### 4-3. 세션 상태

| `session.status` | 참여하기 | 탭했을 때                                    |
| ---------------- | -------- | -------------------------------------------- |
| `loading`        | 비활성   | —                                            |
| `error`          | 비활성   | 오류 안내 + `retry()`                        |
| `anonymous`      | 활성     | 로그인 Drawer 열기                           |
| `authenticated`  | 활성     | `/i/{code}/nickname`으로 이동 (Drawer 안 뜸) |

참여하기 활성 조건은 **`canJoin=true` AND `session.status ∈ {anonymous, authenticated}`** 이다.

### 4-4. 로그인 Drawer 구성

| 실행 환경                             | `type`   | 게스트 선택지 |
| ------------------------------------- | -------- | ------------- |
| WebView 안 (`isNativeContext()=true`) | `member` | 없음          |
| 모바일 웹                             | `guest`  | 있음          |

## 5. 복귀 경로 계약

```
/i/{code}  ──참여하기──▶  Drawer  ──소셜 로그인──▶  OAuth
                                                     │
                          ┌──────────────────────────┘
                          ▼
             온보딩 완료?  ──아니오──▶  /nickname?next=/i/{code}  ──완료──▶  /i/{code}
                          │
                         예
                          ▼
                    /i/{code}
```

- INV-01이 Drawer를 열 때 `SocialLoginButtons`에 `next=/i/{code}`를 **명시적으로 전달**한다.
- `resolvePostLoginPath`는 온보딩이 남았을 때도 `next`를 잃지 않고 온보딩 경로에 실어 보낸다.
- 외부 주소 차단은 기존 `toSafeNextPath`가 담당한다. 새로 만들지 않는다.
- 복귀 지점은 `/i/{code}`다. `/i/{code}/nickname`이 아니다 — 복귀 후 참여 가능 상태를 다시
  확인해야 하기 때문이다(로그인하는 사이 정원이 찰 수 있다).

## 8. Out of Scope

이번 사이클에서 **하지 않을 것**을 명시한다.

- **딥링크 일체** — Universal Link · App Link · 커스텀 스킴 · 카카오 `executionParams` ·
  `.well-known` 정적 파일 · 네이티브 WebView 초기 URL 주입. 별도 feature로 분리했다.
- **VIEW-01 모임 현황 화면** — 라우트도 기획도 없다. INV-01은 버튼 UI만 그린다.
- **`planningType`·`scheduleMode`·`placeMode`별 참여 입력 첫 화면 분기** — 모임 닉네임 화면
  **다음** 단계다.
- **게스트 재입장·비밀번호 검증 정책** — 서버도 "아직 구현하지 않았습니다"로 명시.
- **참여자 목록·모임장 프로필 이미지** — API에 없다. 프로필 자리는 placeholder 유지.
- **정원·마감 실시간 갱신(폴링·소켓)** — 진입 시점 1회 조회로 충분하다고 본다.
- **앱 설치 유도 배너·스토어 이동** — 딥링크 feature와 함께 다룬다.

## 9. 확인 사항 처리 결과 (2026-07-31)

| #   | 항목                         | 처리                                                                                                         |
| --- | ---------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 1   | Drawer 구성 기준             | **확정.** 앱(WebView) 안에서는 게스트 참여를 막는 것이 기획 의도다. §4-4 표가 최종                           |
| 2   | 404·오류 화면 문구와 시안    | **시안 없이 진행.** 기존 토큰과 `CompletionLayout`을 재사용한 최소 화면으로 구현하고, 카피가 나오면 교체한다 |
| 3   | 모임장 프로필 표시           | **placeholder 유지 → Avatar 컴포넌트로 교체.** 아래 단계별 계약 참고                                         |
| 4   | `inv-01.md` 원본 기능표 수정 | **보류.** PM 판단 대기. 본 문서의 축소 범위로 구현을 진행하며, 원본 수정 여부는 구현을 막지 않는다           |

### 3번 — 모임장 프로필의 단계별 계약

```
현재      카드 내부의 색 있는 원 (placeholder)
다음      팀원이 만드는 shared/ui Avatar 컴포넌트로 교체
그 다음   서버가 프로필 이미지를 내려주면 Avatar에 이미지 연결
```

- 기존 `shared/assets/icons/avatar.svg`는 **로그인 화면 전용**이라 여기서 쓰지 않는다.
  INV-01의 모임장 자리는 색이 들어간 표현이 필요하다.
- Avatar 컴포넌트는 **팀원 작업**(#132 `[feat] 아바타 공통 컴포넌트 (Avatar + AvatarGroup)`)
  이므로 이번 이슈에서 만들지 않는다. INV-01은 현재 placeholder를 그대로 두고 진행한다.
- 카드는 세 단계 모두에서 **props 모양이 바뀌지 않도록** 설계한다 — 프로필 표현을 카드 안에
  고정하지 말고 교체 가능한 자리로 둔다. 그래야 Avatar가 들어올 때 카드 계약을 안 건드린다.
