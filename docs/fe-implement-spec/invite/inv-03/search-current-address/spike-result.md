## 0. 선행 확인 (S2)

### ✅ 제품 활성화 — 도메인 등록만으로는 부족하다 (해결됨)

> **결론: 코드 문제가 아니라 앱을 잘못 짚은 것이었다.** 모여 계정에는 카카오 앱이 둘 있고
> 카카오맵은 `MOYEO(ID 1517383)` 에만 활성화돼 있다. `.env.local` 의
> `NEXT_PUBLIC_KAKAO_JS_KEY` 를 MOYEO 키로 교체해 `200` 을 받았다.
>
> 🔴 `NEXT_PUBLIC_KAKAO_CLIENT_ID`(로그인 REST 키)는 다른 앱 것이라 **함께 바꾸지 않는다.**
> 카카오 회원번호가 앱별이라 기존 가입자가 전부 끊긴다.

아래는 원인을 좁혀간 기록이다. 2026-08-10 데스크톱 1차 시도에서 SDK 스크립트가 403으로 떨어졌다.

```
GET https://dapi.kakao.com/v2/maps/sdk.js?appkey=…&libraries=services&autoload=false
403 {"errorType":"NotAuthorizedError","message":"App(모여) disabled OPEN_MAP_AND_LOCAL service."}
```

`Referer` 유무, `libraries`·`autoload` 파라미터 유무와 **무관하게** 같은 응답이다.
도메인 검사에 도달하기도 전에 막힌다.

원인이 코드인지 설정인지는 다른 프로젝트의 키로 갈렸다 — **같은 URL·같은 파라미터에
`ppopgipang-react`의 지도 키를 넣으면 200과 함께 실제 SDK 코드가 내려온다.**

| 키                              | 응답                                                   |
| ------------------------------- | ------------------------------------------------------ |
| 모여 `NEXT_PUBLIC_KAKAO_JS_KEY` | `403 NotAuthorizedError` (OPEN_MAP_AND_LOCAL disabled) |
| 뽑기팡 지도 키                  | `200` + SDK 스크립트 본문                              |

즉 SDK URL·파라미터·로더 코드는 전부 정상이고, **차이는 모여 카카오 앱의 제품 권한뿐이다.**
카카오맵은 `플랫폼 > Web` 도메인 등록과 별개로 앱 단위 제품 활성화가 필요하다.

- [x] 모여 카카오 앱에서 카카오맵(지도/로컬) 제품 권한 활성화
      — 에러의 `OPEN_MAP_AND_LOCAL`이 이 제품이다.
      실제로는 "켜는" 게 아니라 **이미 켜져 있는 MOYEO 앱의 키로 바꾸는 것**이 답이었다.

> 콘솔에서 활성화 항목이 안 보이면 **뽑기팡 앱과 모여 앱의 설정 화면을 나란히 열어 비교한다.**
> 뽑기팡은 같은 키 방식으로 200이 내려오므로, 두 앱의 차이가 곧 켜야 할 항목이다.
> 콘솔 UI에 항목이 아예 없으면 앱 생성 시점에 따라 별도 이용 신청이 필요한 경우이므로
> 카카오 문의로 넘어간다.

> 재확인 방법 (브라우저 없이):
>
> ```bash
> KEY=$(grep '^NEXT_PUBLIC_KAKAO_JS_KEY=' apps/web/.env.local | cut -d= -f2- | tr -d '\r\n"')
> curl -s -w '\nstatus=%{http_code}\n' \
>   "https://dapi.kakao.com/v2/maps/sdk.js?appkey=$KEY&libraries=services&autoload=false" | head -c 300
> ```
>
> `status=200`이면 활성화 완료다.

### 도메인 등록 (완료)

도메인 등록 자체는 **앱 단위 설정**이라 카카오톡 공유용으로 등록해 둔 것이 지도 SDK에도
그대로 적용된다. 스크립트 호스트만 다르고(공유 `t1.kakaocdn.net` / 지도 `dapi.kakao.com`)
도메인 검증은 같은 `앱 설정 > 플랫폼 > Web`을 쓴다. 제품을 켠 뒤에는 이 등록이 유효해진다.

- [x] `http://localhost:3000` — 공유 기능으로 등록 완료
- [x] `https://moyeo-dev.vercel.app` — 동일
- [x] `https://moyeo-web.vercel.app` — 동일
- [x] `apps/web/.env.local` 의 `NEXT_PUBLIC_KAKAO_JS_KEY` (32자)
- [x] `http://192.168.45.10:3000` — 실기기 dev용으로 추가 등록 (2026-08-10)

등록 여부는 Referer를 바꿔가며 확인할 수 있다. **`200` 등록됨 / `401` 미등록 / `403` 앱이 틀림.**

```bash
KEY=$(grep '^NEXT_PUBLIC_KAKAO_JS_KEY=' apps/web/.env.local | cut -d= -f2- | tr -d '\r\n"')
curl -s -o /dev/null -w '%{http_code}\n' -H "Referer: http://192.168.45.10:3000" \
  "https://dapi.kakao.com/v2/maps/sdk.js?appkey=$KEY&libraries=services&autoload=false"
```

| Referer                      | 응답                       |
| ---------------------------- | -------------------------- |
| `http://localhost:3000`      | `200`                      |
| `http://192.168.45.10:3000`  | `200`                      |
| `http://192.168.45.213:3000` | `401` (등록 안 한 이전 IP) |

> LAN IP는 망이 바뀌면 달라진다. `/spike` 첫 화면이 현재 origin을 띄워주니 그 값으로 등록한다.

### ⚠️ 실기기 WebView만 origin이 다르다

`apps/native/app/index.tsx:25-29`가 dev 빌드에서 웹 주소를 이렇게 정한다.

```ts
const devHost = Constants.expoConfig?.hostUri?.split(':')[0];
const WEB_URL = __DEV__ && devHost ? `http://${devHost}:3000` : ...;
```

즉 앱 WebView가 보는 origin은 `http://192.168.x.x:3000` 이고, 이건 **공유 기능 테스트로는
등록됐을 리 없으며 네트워크가 바뀔 때마다 달라진다.** 데스크톱·모바일 웹이 멀쩡한데
앱에서만 지도가 안 뜨면 A2 실패가 아니라 이 origin 문제일 가능성이 높다.

대응 (택1):

- [ ] 현재 LAN IP origin을 카카오 콘솔에 임시 등록 — 가장 빠르지만 망이 바뀌면 다시 해야 한다
- [ ] 스파이크를 develop에 올려 preview 배포한 뒤, `moyeo-dev.vercel.app`을 띄우는
      preview 빌드로 확인 — origin이 이미 등록된 도메인이라 재등록이 필요 없다

> 데스크톱 브라우저(`http://localhost:3000/spike/map`)에서 먼저 지도가 뜨는지 본다.
> **여기서 실패하면 A2 문제가 아니라 설정 문제다.**

### 🔴 dev 서버가 http라서 iOS에서는 지도가 비어 보인다 (A2 실패 아님)

**카카오 지도 SDK는 필요한 모든 URL의 프로토콜을 `location.protocol` 에서 파생한다.**
그래서 dev 서버를 `http://<LAN-IP>:3000` 으로 열면 세 갈래가 전부 cleartext http로 나간다.

| 갈래          | 코드                                                                    | 우회            |
| ------------- | ----------------------------------------------------------------------- | --------------- |
| 지도 번들     | `sdk.js`: `s = "https:"==location.protocol ? "https:" : "http:"`        | 됨 (직접 주입)  |
| 로컬 API      | `services.js`: `DOMAIN = PROTOCOL + "//dapi.kakao.com"`                 | 됨 (직접 fetch) |
| **지도 타일** | `kakao.js`: `cd = "https:"==location.protocol ? "https://" : "http://"` | **안 됨**       |

앞의 둘은 스파이크에서 https로 우회했지만, 타일은 프로토콜 접두사가 번들 평가 시점의 클로저
변수라 밖에서 바꿀 수 없다. `URI_FUNC` 를 덮어써도 `cd` 가 앞에 붙어 `http://https://…` 가 된다.

관측 결과 (2026-08-10, 실기기):

| 기기       | 지도 타일   | 타일 프로브 (같은 파일, 프로토콜만 다름) |
| ---------- | ----------- | ---------------------------------------- |
| Android 앱 | 보임        | —                                        |
| iOS 앱     | **안 보임** | `http ❌ / https ✅`                     |

프로브는 `t1.daumcdn.net/mapjsapi/images/transparent.gif` 를 `<img>` 로 받아본 것이다.
서버는 두 프로토콜 모두 `200` 이므로, 기기에서 갈린 것은 **WebView의 cleartext 정책**이다.

> **이것을 A2 실패로 적으면 안 된다.** 막힌 것은 dev 환경의 전송 프로토콜이지 지도 동작이 아니다.
> 프로덕션(`https://moyeo-web.vercel.app`)에는 이 경로가 없다.
>
> iOS 확인은 https에서 해야 한다 — `moyeo-dev.vercel.app` 은 이미 등록돼 있으므로
> preview 배포가 가장 싸다. (`next dev --experimental-https` 는 자체 서명 인증서라
> iOS에서 프로파일 설치·완전 신뢰까지 필요해 번거롭다)

### 역지오코딩은 `KA` 헤더를 요구한다

`Authorization: KakaoAK {JS키}` 만으로는 `AccessDeniedError` 가 난다
(`KA Header is required but neither os nor origin field is given`). `services.js` 가 함께 싣는
헤더가 있다.

```
KA: sdk/{version} os/javascript lang/{lang} device/{platform} origin/{encodeURIComponent(origin)}
```

`origin` 은 콘솔 등록값과 대조되므로 **페이지의 실제 origin(http 그대로)** 을 보낸다.
https로 바꿔 보내면 미등록 도메인이 되어 거부당한다. 이 헤더를 붙이면 `200` 과 정상 주소가 온다.

### 검토했다 접은 대안

RN + 카카오 지도 자료는 대부분 **WebView에 인라인 HTML을 주입하는 구성**을 전제한다.
그 구성은 페이지 origin이 `about:blank`·`file://` 이라 우리와 전제가 다르고, 거기서 나온
처방을 그대로 가져오면 오히려 후퇴한다. 같은 자료를 다시 만났을 때 흔들리지 않도록 남긴다.

| 대안                                          | 접은 이유                                                                                                                 |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 좌표 변환을 REST API로 (RN에서 호출 → 브리지) | 우리 origin은 등록돼 있어 SDK `Geocoder` 가 그대로 된다(200 + 정상 주소 확인). 게다가 **웹 1차 릴리스(§5)가 깨진다**      |
| iOS ATS 예외 (`NSAllowsArbitraryLoads*`)      | 프로덕션은 https라 필요 없다. 네이티브 재빌드 비용 + 심사 소명 부담 + **배포하지 않을 설정을 검증하게 된다**              |
| 카카오 공식 답변의 inline HTML 샘플           | `source={{html}}` 은 origin이 없어 ATS를 열어야 뜨고 `Geocoder` 는 못 쓴다. 카카오도 "WebView는 재현·검증 못 했다"고 명시 |
| 컨테이너 높이 0 (`onLayout` 으로 크기 확보)   | 측정으로 배제. 지도 생성 시점 컨테이너 `390×359px`                                                                        |

> origin이 없어도 **기본 지도까지는 뜬다** — `sdk.js` 는 Referer 없이도 200이고 타일은 인증 없는
> CDN 이미지다. 갈리는 건 로컬 API(`coord2Address`)로, 여기서 origin을 검사한다.
> 위 자료들이 Geocoder에서만 막힌 이유가 이것이다.

### 특이사항

**주2 — 🔴 `spec-fixed.md` §4-4의 확정 방식이 성립하지 않는다.**

관측(2026-08-10, 모달 진입): `1. picker 열기` → `3. CTA 흐름` 을 누르면 부모 화면이 아니라
**검색 화면(`/spike/slot/inner`)에 남는다.**

원인은 `replace` 의 성질이다. §4-4는 "picker 쿼리를 replace로 걷어낸다"고 적었지만,
**`replace` 는 항목을 제거하지 않고 덮어쓴다.** 깊이가 줄지 않는다.

```
[INV-03, 검색, 위치확인]
  → router.replace(검색URL)  →  [INV-03, 검색, 검색]   ← 깊이 그대로 3
  → 호출부의 router.back()   →  검색                    ← INV-03 아님
```

§4-4의 "히스토리 깊이가 늘지 않는다"는 맞다. 하지만 INV-03에 도달하려면 깊이가 **줄어야**
한다. picker를 `push` 로 열었으므로 그 항목은 `pop` 해야 한다.

독립 페이지(새로고침) 진입은 이 문제가 없다. `onClose` 가 `replace(부모)` 라서 replace 두 번으로
목적지에 도착한다. **즉 이 결함은 모달 진입에서만 난다.**

검토한 선택지:

| 안                                        | 결과                                                                                       |
| ----------------------------------------- | ------------------------------------------------------------------------------------------ |
| picker를 `replace` 로 열기                | ❌ 뒤로가기가 검색까지 닫는다. iOS 스와이프·브라우저 back은 핸들러를 우회하므로 §4-2 위반  |
| CTA에서 `back()` 두 번 연속               | ❌ §4-4가 이미 신뢰할 수 없다고 배제한 방식                                                |
| CTA에서 부모 URL로 직접 `replace`         | △ 동작은 한다. `[INV-03, 검색, INV-03]` 이 남아 완료 후 뒤로가기를 누르면 검색이 다시 뜬다 |
| **CTA에서 `back()` → 닫힌 뒤 `onSelect`** | ✅ 권장. 두 동작을 같은 tick이 아니라 **순차**로 태운다                                    |

권장안은 CTA가 `router.back()` 으로 picker 항목만 pop하고, `isPickerOpen` 이 `false` 로
바뀌는 시점에 보류해 둔 `onSelect(draft)` 를 실행하는 것이다. §4-4가 배제한 것은 _동기적으로
연속된_ `back()` 이지 순차 실행이 아니므로 그 논거와 충돌하지 않고, 히스토리도
`[INV-03]` 으로 깨끗하게 남는다. 대신 검색 화면이 한 프레임 보일 수 있어 §4-4가 이미 적어둔
완화책(`isPickerOpen` 동안 검색 본문 렌더 유지)이 함께 필요하다 — R3와 같은 처방이다.

> 이 절은 스파이크 관측 기록이다. **`spec-fixed.md` §4-4 자체의 수정은 아직 하지 않았다.**
